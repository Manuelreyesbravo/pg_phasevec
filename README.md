# pg_phasevec

**Readings with provenance: what a sealed reader understood of each row, and whether it still holds.**

Vector search over a table has a quiet failure mode. The embedding was computed once, the row changed, and the index now answers from a memory of a row that no longer exists -- and nothing says so. pg_phasevec makes that visible. It stores, for each row, the code a sealed reader produced *together with the hash of the exact text it read and the identity of the reader that read it*. You search by meaning, and every answer tells you whether the reading it matched still holds for the row as it is now, or whether the row moved underneath it.

No cloud API and no network call: the reader is yours and local, and the codes live in your database next to the rows they describe.

## Why

A reading in pg_phasevec carries three things a bare embedding does not:

* **who read it** -- a reader is identified by the sha256 of its weights (adapter and heads included) and the compute it runs on. Readings taken by different readers are never compared, so swapping a model does not silently mix two coordinate systems.
* **what it read** -- the hash of the exact text. A row edited after it was read becomes **stale**: it is not searched, and it is never returned as a confident wrong answer. A reading of text that is no longer there is refused.
* **when** -- so the age of the memory is a column, not a guess.

## The model

* A **reader** is sealed. `reader_register(name, model_sha256, dims)` records what it is; a trained reader carries a manifest (base, adapter and heads shas, pooling, MRL dims) sealed by whoever serves it.
* A **watch** is what must be findable: a source table, its key column, and one named recipe for the text to read (an expression over each row). `find()` refuses to answer below the watch's `min_coverage`, so a half-filled index does not quietly answer from the rows it happens to have.
* A **reading** is what a reader understood of a row: the hash of the text, its codes, and when. Each one has a state -- pending, fresh, stale, foreign (a different reader), orphan (the row is gone), or failed (the reader said why) among them -- and coverage() shows the spread.

## Install

```sh
make PG_CONFIG=/path/to/pg_config
make install PG_CONFIG=/path/to/pg_config
```
```sql
CREATE EXTENSION pg_phasevec;
```

PostgreSQL 18 or newer. No other extension is required. `verify()` and `verify_one()` judge each proof in a background worker of its own (below): they need free slots of `max_worker_processes` (8 by default, shared with parallel query and logical replication): `verify_one()` one, `verify()` two at a time (the proof's session and its keeper, below); a proof itself starts no parallel worker. The library is loaded by the worker by its path, with no `shared_preload_libraries`.

The build is portable: it adds `-O3` to the server's own `CFLAGS` and nothing tied to the build machine's CPU. `make PHASEVEC_NATIVE=1` adds `-march=native` for a build that only has to run where it was compiled (until 0.19.0 that was the default, and a binary built on a newer CPU could stop with `SIGILL` on an older one).

## A walk through it

```sql
CREATE EXTENSION pg_phasevec;

-- 1. Seal a reader by the sha256 of its weights and its dimensionality.
SELECT phasevec.reader_register('vec', '<model_sha256>', 1024);

CREATE TABLE docs (id int PRIMARY KEY, body text);
INSERT INTO docs VALUES (1, 'apple'), (2, 'banana'), (3, 'cherry');

-- 2. Watch the table: read the expression `r.body` of each row, keyed by `id`.
SELECT phasevec.watch('docs', 'docs'::regclass, 'id', 'r.body', 'vec');

-- 3. Fill it. next() hands out the rows that still need reading, each with the hash
--    of its exact text; the sealed reader turns each into codes (a 64-bit sketch and
--    a per-dimension code); record() stores them against that hash.
SELECT phasevec.record('docs', key, 'vec', text_hash, code64, code)
  FROM phasevec.next('docs') AS r,  -- key, body, text_hash
       LATERAL your_reader(r.body) AS codes(code64, code);

-- 4. Ask in words: the watch's reader reads the question, and phasevec answers in
--    your own snapshot, never from stale text.
SELECT key, score, state, read_at
  FROM phasevec.search('docs', 'which fruit is red?', 10);

-- ...or query with codes you computed yourself:
SELECT key, score, hamming, state
  FROM phasevec.find('docs', <q64>, ARRAY[/* per-dimension query code */]::smallint[], 10);

-- rows like a given one:
SELECT key FROM phasevec.alike('docs', '2', 5);
```

Edit a watched row and its reading turns `stale` in the same transaction; `find()` then withholds it, or returns a partial answer only when the caller asks for one with `p_partial => true`. Point the watch at a new reader with `reader_switch()` and every old reading becomes `foreign` -- coverage drops, and nothing from the old reader is mixed in.

## What it guarantees, and what it trusts

* **Guaranteed.** A reading names the reader and the exact text it was taken from. A row changed after it was read is reported as stale, not matched as if fresh; a reading of the old text is refused. Readings from different readers are never compared. A deleted row leaves an orphan reading you can see, not a silent ghost in the index. `find()` refuses below `min_coverage`.
* **Trusted.** The reader is yours. pg_phasevec stores and searches the codes a sealed reader gives it and holds them to that reader's sha; it does not vouch for what the weights behind that sha actually do. Keep the reader sealed and local.
* The maintenance surface (`ivf_build`, `ivf_maintain`, `ivf_maintain_all`, `ivf_absorb`, `counts_compact`, and the internal sweep/delta) is `REVOKE`d from `PUBLIC`. The search functions are `SECURITY DEFINER` with a pinned `search_path` (they do not run with the caller's privileges, as this page said until 0.20.0): `search`, `find`, `find_ivf` and `find_npu` are open to `PUBLIC` and give any role with `USAGE` on the schema the keys, scores and reading states of every watch (not the rows' text, not verdicts); `alike` and `find_hybrid` are revoked from `PUBLIC`. Revoke the open ones from `PUBLIC` where keys are themselves sensitive. What shows verdicts (`recall`, `disputes`, `replacement`, `truth_coverage`, `brief`) shows a watch only to a role that may `SELECT` its table (0.20.0, below).

## Watching its own recall

A search does not fail when it degrades: `find_ivf` and `find` keep returning k plausible rows. Since 0.17.0 pg_phasevec measures what a watch is actually served and compares it with a baseline its owner approved.

```sql
-- served by the coarse index with nprobe 16 and m 200 (the defaults), 200 sampled rows, recall@10
SELECT phasevec.recall_approve('docs');
-- served by find with m 1000 (a watch without a coarse index picks find by itself)
SELECT phasevec.recall_approve('notes', p_m => 1000, p_via => 'find');

SELECT watch, verdict, baseline, current, drift, k, sample, via, nprobe, m FROM phasevec.recall_check();
```

* **What it measures.** Each sampled row asks with its own reading (and is left out of both answers). What is served is the path stored at approval: `find_ivf` with its `m` and `nprobe`, or `find` with its `m`. The truth is `find` with `m` = every live reading of the watch -- `find` prefilters by Hamming distance and rescores only `m` candidates, so with a small `m` it is not exact. recall@k is the share of the true top-k the served top-k holds, counted by score (two rows with equal codes are not a miss), rounded to four decimals.
* **Verdicts**, with pg_recall_guard's bands: `ok` if `current >= baseline - 0.02`, `degraded` if `>= baseline - 0.10`, `critical` below. A watch that cannot be measured -- no baseline, no such watch, no coarse index for `find_ivf`, its reader switched, more than half of the sample deleted, changed or superseded -- is a row with verdict `COULD NOT MEASURE: <why>`, never an exception. Both searches run with `p_partial => true`: a watch below `min_coverage` is measured on what is read.
* **The settings are the stored ones.** Lowering `nprobe` or `m` in a session changes nothing; the check degrades when the data or the index does. Measured: a watch served by `find` with `m` 50 reads 1.0 at 500 rows and 0.76 at 1000 (more rows behind the same `m`); new rows absorbed into lists trained without them read degraded; an index rebuilt with far too many lists for its `nprobe` reads critical. Rebuilding, or serving with a larger `m` and approving that, reads `ok` again.
* **Who may.** All three functions are `SECURITY DEFINER` with a pinned `search_path` and revoked from `PUBLIC`, as is `phasevec.recall_baseline`. A monitoring role gets the check and nothing else: `GRANT USAGE ON SCHEMA phasevec TO monitor; GRANT EXECUTE ON FUNCTION phasevec.recall_check(text) TO monitor;`.
* **Limits.** The truth is `find` over every live reading, so a check costs about `sample x rows` cosine scores (here ~30 us per row per question: 2000 rows, 200 questions, ~12 s); size `p_sample` to it, and keep the tables analyzed -- without statistics the same check ran ~20x slower. `find` takes at most `m` = 100000: above 100000 live readings the truth is itself prefiltered and the guard can read better than what is served. The sample is a set of keys: re-approve when most of it is gone.

0.17.0 also fixes the coarse index kept in memory across an extension reinstall: after `DROP EXTENSION` and `CREATE EXTENSION` on a server that had not restarted, the new watch matched the old installation's copy (same watch id, same generation) and `find_ivf` answered short without a word. Every kept copy now carries the installation it belongs to (`test/sql/ivf_reinstall.sql`). The copy shared by the cluster is now kept under a new name (its format changed): upgrading the library leaves the old one in shared memory until the server restarts, so restart after installing 0.17.0 to release it. On PostgreSQL 18 there is no shared copy (it needs `GetNamedDSA`, new in 19): each connection keeps its own, `phasevec.shared_ivf_cache` is `off` and cannot be turned on, and the answers are the same. From 0.10.0 to 0.16.0 the library did not build on PostgreSQL 18 at all; 0.17.0 does, and its suite runs on 18 and 19.

## Security

0.16.0 is a security-hardening release. The SPI cursors that drive index build and maintenance skip rows with a `NULL` code instead of dereferencing it; every count, dimension and probe argument is bounded before it reaches an allocation, and an overflow in `k * dims` is caught; the proof clock cannot re-enter itself; a path built for the reader socket is refused if it would truncate; and the maintenance functions are revoked from `PUBLIC`. The checks have a regression test in `test/sql/security.sql`.

0.20.0 fixes what twelve reviews of 2026-11-05 and 2026-11-06 found in the truth layer and the coarse index. The last eleven ran attacks against eleven cuts of this release, which were never published; what they broke is fixed here too. The eighth found that each of the four before it had closed one piece of the verifier's session that decided verdicts and left the next one open, and a proof no longer runs in its verifier's session at all. The third one's findings came from one root -- phasevec ran code that was not its own (a watch's recipe, a proof) in more than one way, some of them with the rights or the settings of whoever happened to call it -- and there is now one way (`src/phasevec_guard.c`):

* **One guard for code that is not phasevec's, and it is a sealed room.** A recipe and a proof run in a subtransaction of their own, always rolled back, as one named role, in a security-restricted operation, read-only. Nothing that existed before the guard is in reach. The session's open cursors: the ones `pg_cursors` lists are frozen while it runs (PostgreSQL itself then refuses to run or close them), a query begun before it cannot be run inside it, and `FETCH`, `MOVE` and `CLOSE` take only cursors opened inside it. Of the commands only `SET`, `SHOW`, `EXPLAIN`, `DECLARE`, `FETCH`, `MOVE`, `CLOSE`, `CALL` and `DO` run (`NOTIFY`, `LISTEN`, `PREPARE`, `DEALLOCATE`, `DISCARD`, `LOAD` and the rest are refused). Of the system's own functions every one that only reads (stable or immutable) runs, and of the volatile ones only a reviewed few: the clock, `pg_sleep`, random numbers, `set_config`, transaction-level advisory locks (all of them end with the guard's rollback). `pg_notify`, session-level advisory locks, `setseed`, `currval` and `lastval`, the large-object descriptors, `pg_cancel_backend`, `pg_terminate_backend` and every other volatile system function are refused, and so are `pg_cursor` and `pg_prepared_statement`, which read the session's own statements, `EXPLAIN EXECUTE`, which shows one of them (and with `ANALYZE` runs it), and `txid_current()` and `pg_current_xact_id()`, which are stable but give the session's transaction an id no rollback takes back. The session's temporary objects are its own too: inside the guard `pg_temp` is searched last (appended to the author's `search_path` when it does not name it), and every temporary object is refused, by what a query uses and not by how it names it: every query parsed or planned inside the guard is walked for the objects it depends on (tables and views, types and domains, functions, operators, collations, and what a `regclass`-like constant names), as PostgreSQL walks a view's query to decide whether the view is temporary, and one in a temporary schema is refused -- named, found through `search_path`, as the child of a permanent table it inherits from, inside a SQL function (inside the guard no SQL function but the system's is inlined, so its body is parsed as a query of its own; a body written `BEGIN ATOMIC` is checked when it is planned), or in a plan the session cached before the guard ran (a session whose functions made a plan which may hold one of its temporary objects has its cached plans parsed again before a guard runs code; a session with no temporary object, or no such plan, pays nothing, and so does a statement the client sends, which no code in a guard can run: in the sixth cut a session that wrote to its own temporary table threw away every cached plan at its next write to a watched table, the watch trigger's and its own prepared statements, 0.56 ms per single-row write against 0.09 ms, now 0.09-0.11 ms, `test/sql/truth_lookup.sql`). The walk is phasevec's own on PostgreSQL 18 and runs beside `collectDependenciesOfExpr` on 19: in the sixth cut the `RETURNING` type of `JSON_VALUE` and `JSON_QUERY` (with `NULL ON ERROR`, in no other node) went past both, and a `regconfig` or `regdictionary` constant past 18's. The session's timeouts (`transaction_timeout`, `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, `idle_session_timeout`) and `exit_on_error` cannot be changed, by `set_config`, `SET`, or a function's `SET` clause. In the second cut a proof set `transaction_timeout` and ended the verifier's connection with a `FATAL` before any verdict was written, so every later `verify()` of the watch died the same way; another released the verifier's own advisory locks; another chose its `random()` seed. In the third, which had no subtransaction for a recipe, a table owner's recipe read a superuser's open cursor over a table the owner could not read and sent the rows out with `NOTIFY`, delivered at the superuser's `COMMIT` (in `brief()`, and in the watch trigger of every writer); and a proof read, used up and printed in its error the verifier's open cursor (`test/sql/truth_guard.sql`, `test/sql/truth_sealed.sql`). In the fourth, a verifier's temporary tables named like the author's took their place in the proof (`pg_temp` was searched first: the author's `search_path` did not name it), and `verify()` recorded, and `brief()` served, `verified` for claims the real tables refute; a temporary function did the same, and a proof printed in its error a statement the verifier had prepared, its constants included (`test/sql/truth_session.sql`). In the fifth, only temporary tables and functions were refused, by the kind of range-table entry they came in: a verifier's temporary view (a subquery entry since PostgreSQL 16), enum, domain, operator or collation decided a proof the author's own objects refute, and `verify()` recorded and `brief()` served it as `verified`; a PL/pgSQL function with its own `search_path`, run once by the verifier before `verify()`, did it through its cached plan (`test/sql/truth_temp.sql`).
* **A proof runs in a session of its own (eighth review).** Four reviews in a row found one more piece of the verifier's session that decided a verdict, each closed where it was found: its settings' values (third), its temporary objects (fourth to sixth: in the sixth a name looked up while a proof ran, `to_regclass('pg_temp.v')` or a cast of text to `regclass`, found the verifier's, and `verify()` was then refused in any session that had one), which custom placeholders it had (seventh); and in the eighth its uncommitted writes and DDL (a verifier deleted the overdue invoice, verified, put it back and committed: the proof had judged a state no other session ever saw, and the verdict was recorded and served), its `session_user` (after `SET SESSION AUTHORIZATION`, or under a policy `USING (tenant = session_user)`) and its `application_name`. Now `verify()` and `verify_one()` start a background worker (`RegisterDynamicBackgroundWorker`) connected to the database as the claim's author: a new session of the author, as a client would get one -- its `session_user` is the author, it has what `postgresql.conf`, `ALTER SYSTEM` and `ALTER DATABASE`/`ALTER ROLE ... SET` give every new session of that author, and its `session_preload_libraries` (a role that does not log in is let in: the verifier may act as it). There each claim is judged in a transaction of its own, at READ COMMITTED, in the guard, with what the author's session had changed on top, and reads only what is committed: no row or DDL the verifier has not committed, no temporary object, cursor or prepared statement of the verifier's, none of its settings or its identity. The verifier chooses the claims and sends them to the worker (`shm_mq`), up to eight ahead of their answers; one worker serves a call and an author. Since the ninth review the worker also takes each claim's row and records its verdict, in the transaction that judges it (below). A verifier that is canceled, fails or ends ends its worker. With no background worker free, a claim is not judged: nothing is recorded, it stays due, and its row in `verify()` says why (`verify_one()`: an error). What this took away: the refusal to verify in a session with temporary objects, the two passes over a call's claims and the refusal to judge in a session with a placeholder the author did not have (below), the halt marks in shared memory (below), and the settings pinned for a whole `verify()` call (`test/sql/truth_own_session.sql`, `test/truth_race.sh`). What a recipe needs stays: it renders in the session that reads or writes the row (the watch trigger in the writer's, `brief()` in the reader's), so the guard's frozen cursors and its walk for temporary objects still guard it.
* **A verdict is about a committed state that does not depend on its verifier (ninth review).** In the eighth cut the verifier took and recorded the claims in its own transaction. A verifier with an uncommitted write that refuted a claim had the proof judge the committed state before that write (a proof's session cannot see it), and committed, together with the write, a `verified` that no committed state ever made true; `brief()` served it. Now the worker takes the claim's row, judges it and records the verdict in a transaction of its own, and commits it before it answers. The verifier writes nothing (`verify()` gives its transaction no transaction id): a `ROLLBACK` of the verifier keeps the verdicts its proofs reached, and it may verify again in the same transaction or statement. A transaction that has written may not verify, and since the sixteenth review neither may a read-only one (below): `verify()` and `verify_one()` refuse one with a transaction id (a write, DDL, `LOCK TABLE ... ACCESS EXCLUSIVE`, an `assert()`), whose writes would be judged as if they were not there. A worker commits with `synchronous_commit = off`: a crash can lose its last verdicts, and their claims are due again (`test/sql/truth_verifier.sql`).
* **A verifier never waits without its deadlines (ninth review).** A claim goes to the worker without waiting (`shm_mq_send` with `nowait`), in the loop that keeps the proof's clock and 5 s more, the start of a worker, `p_budget` and the lock check; a claim larger than half the queue (64 kB) goes alone, in pieces. In the eighth cut a claim over 64 kB blocked the verifier inside the send: behind a proof that catches `query_canceled`, or a worker waiting for a lock, nothing ended the call but a cancel. A proof that waits for a lock the verifier's transaction holds, directly (a session's advisory lock) or through other sessions (an `ALTER TABLE` queued behind the verifier's read of a table, with the proof's read queued behind it), would wait as long as the verifier waits for it: the verifier walks the waits (`pg_blocking_pids`, session to session) and stops with an error. The eighth cut saw only a direct wait: the proof waited out its clock and was recorded `refuted`, and the `ALTER TABLE` and every reader of the table waited a clock per claim. A proof still waiting for another session's lock when its clock ends (or past its author's `lock_timeout`) is not judged, with the reason: a lock another session holds is not the proof's answer (`test/truth_worker.sh`); since the twelfth review neither is one that waited for such a lock and then ended after its clock (below).
* **Verdicts move forward in time, and an author's settings do not end its workers (tenth review).** In the ninth cut `verify_one()`'s worker judged before it took the claim's row (only `verify()`'s took it first), then waited for the row a `verify()` worker held while it judged; when that one recorded `refuted` (the claim had turned false in between), `verify_one()` wrote its own `verified`, read before, over it, `brief()` served it and `verify()` left the claim alone for `p_every`. Now every worker takes the claim's row before it judges it, whatever it was sent for (`verify_one()` takes it due or not, and waits for it), so of two judgments of a claim the one that reads later commits later; and `_truth_set` does not replace a verdict read after the judgment it records, nor `_truth_halted` a verdict read after the proof began (a record of an earlier run, a proof that took too long or ended its session, can still arrive after a newer verdict, and is dropped) (`test/truth_order.sh`, `test/sql/truth_order.sql`). The worker is phasevec's session, not its author's: before it connects it pins `transaction_timeout`, `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, `idle_session_timeout` and `exit_on_error` over whatever the database and the role set (an ordinary role may `ALTER ROLE` itself `SET transaction_timeout = '1ms'`: in the ninth cut every worker of its claims then ended before it judged, nothing was recorded, its claims kept their old `verified` in `verify()`, `verify_one()` and `brief()`, and with `p_n` they held the head of the queue, so other authors' false claims were never refuted). The proof's clock is its only time limit; a proof still waiting for a lock at its clock is not judged, as before, and neither is one the deadlock check makes give way. A claim that still cannot be judged for its author's sake -- a new session of its author ends before it judges, twice, without another process ending it; an error outside the proof, twice; a placeholder its author's every new session gets -- is recorded as tried, and once no session of an author starts in a call, the rest of that author's claims in it are recorded the same way without trying again (`test/truth_unjudged.sh`). The tenth cut kept such a claim's verdict for one `p_every` more with marks of its own (`truth.unjudged_at`, `unjudged_until`, `unjudged_why`, `tried_at`); the eleventh review found that this, like every other way judgment can stop, needed one rule instead, below, and the marks are gone. This closed one way for an author to end its own workers, not every way: it could still terminate them itself (`pg_terminate_backend` works on a role's own sessions), and until the twelfth review its claims then held the head of the queue (below).

* **Safety does not depend on liveness (eleventh review).** The eleventh review found four more ways to stop judgment from moving while the old verdict was still served: a role with no grants filled the shared lock table with session advisory locks, a proof failed `out of shared memory` and a true claim was recorded `refuted`; an `assert()` of a key left open, by any role that may assert, held the claim's row for as long as it stayed open, `verify()` skipped the claim and recorded nothing, `verify_one()` gave up, and `brief()` served the old `verified` after the committed state refuted it; once `p_n` claims were stale (their rows edited and not asserted again) they sorted first in every call (the due list put a stale claim's `tried_at` first, and the stale path set it to `NULL`; the comment that said such a claim "never holds the head of p_n" was wrong), and no other claim was judged again; and an author holding its own claims' rows in an open transaction had them skipped, unrecorded, at the head of the queue, so other authors' false claims were never refuted. Three rules replace the patches:
  * *A verdict serves while it is fresh.* A `verified` or `refuted` of a proof serves only while it was judged within its watch's horizon, `phasevec.watches.max_age` (1 hour by default; the owner sets it: `UPDATE phasevec.watches SET max_age = '3 hours' WHERE name = 'estado'`). Past `verified_at + max_age`, `_verdict()`, `brief()`, `recall()` and the rest read `unproven` -- judged at the moment they read (`clock_timestamp()`; until the twelfth review the start of the reader's transaction, below) -- whatever kept the claim from being judged again: a row held open, a lock, the server, no worker free, a verifier that does not run. The word stays `unproven` (SQL that reads `phasevec.truth` compares it), and since when is `verified_at + max_age`. A halted claim (its proof ends its session: not run again) and a `refute()` of a key with no proof (nothing judges it again) have no horizon. Choose `max_age` longer than the time `verify()` takes to come round every claim: `ceil(claims / p_n)` calls, each `p_every` or the cron's interval apart, whichever is longer, and one call more (a claim judged just after the last call's `p_every` waits for the next). With 1000 claims, `p_n` 100 and a call every 10 minutes that is 100 minutes or more, and at the default hour about 400 of the 1000 read `unproven` at any time (measured at 60x speed, below); with `p_n` 2000 every claim is judged every 10 minutes and none does.
  * *The due queue is a fair rotation.* A claim's turn is spent before it is taken, judged or recorded, in a transaction of its own committed at once, in `phasevec.attempts` (unlogged, the owner's, written only by phasevec's own sessions, so no other session can hold its rows; after a crash the rotation starts again from when each claim was asserted), and since the twelfth review by a session its author cannot end: `verify()`'s keeper, a session of the extension's owner, spends the turns of the claims bound for their author's session before that session gets them (in the eleventh cut that session spent them itself, below). `_truth_due` takes the claims whose turn is oldest first, a claim never tried from when it was asserted. Whatever becomes of an attempt (judged, the row held by another transaction, a stale text, an error that is not the proof's, a session that ends, before or while its proof runs), the claim goes behind every claim that waits: of N claims due, each is tried within `ceil(N / p_n)` calls that run their `p_n`. It is one queue, not a round per author: with a round per author, an author of few claims is tried more often and one of many waits longer than `ceil(N / p_n)` calls; with one queue no author holds its head. An `assert()` does not give a claim a new turn. A call that finds no worker free (for the keeper or for the author's session) tries nothing, and the claims it did not reach keep their turn: since the thirteenth review both are started before any turn is spent (below).
  * *Only the proof's own logic decides its verdict.* An error in a proof is its answer (`refuted`) when it comes from what the proof computes: its data (`22`), constraints (`23`), SQL and rights (`42`), what it raises (`P0`), a feature it may not use (`0A`), a cardinality (`21`), a program limit it reaches (`54`: too deep a recursion, too complex a statement, which the same proof reaches again), and every class not listed next. It is not an answer when it comes from the server or from other sessions: connection (`08`), transaction rollback (`40`: serialization, deadlock), insufficient resources (`53`: out of shared memory, out of memory, disk full, too many connections), lock not available (`55P03`), operator intervention (`57`: shutdown, cancel), system error (`58`), configuration file (`F0`), foreign data wrapper (`HV`), internal error (`XX`, the server's or phasevec's own). Then nothing is judged, the verdict stays as it was, and the horizon decides how long it serves. One of those classes that the proof raises itself (PL/pgSQL `RAISE ... USING ERRCODE`) is its answer. A lock wait at the clock, a deadlock and a `lock_timeout` are not answers either: until this review they recorded `unproven`, now nothing (`verify_one()` says it could not judge the key, and why).

* **What is the proof's own, and when (twelfth review).** The twelfth review found three places where something that was not the claim's decided what was recorded or served, each against a rule the eleventh had stated:
  * *Only the proof's own work can refute it by time.* A wait for a lock another session held counted against the proof's clock: a lock let go just before the clock ended (a writer's `LOCK TABLE`, or a session advisory key the proof takes, held by a role with no grants) left the proof to finish after its clock, and a true claim was recorded `refuted` ("the proof took longer than 1000 ms"). The eleventh cut told a wait apart only if it was still going when the timer fired. Now a proof that waited for a heavyweight lock at all (a relation, a row's transaction, an advisory key) and ended after its clock is not judged: PostgreSQL arms its deadlock timer for every such wait, and the time it was armed stays after the wait ends, so a wait that began after the clock did is known exactly. The wait's time is not taken off the clock instead: PostgreSQL records when a wait began, not how long it lasted, and sampling misses short waits. A proof slow by itself is still refuted for its time.
  * *A turn is spent by a session its author cannot end.* The worker that spent a claim's turn was the author's own session, and an author may terminate its own sessions: one that terminated its proof sessions before they spent anything (a loop of `pg_terminate_backend` over its own `pg_stat_activity` rows, 610 workers in 25 s) kept its claims unspent at the head of the queue, and no other author's claim was tried again -- 20 false claims of another author were served `verified` through eight calls, against a bound of five. Now `verify()` starts a keeper, a session of the extension's owner, which spends the turns of the claims queued for an author's session, a batch at a time, in a transaction of its own, before any of them is sent; the author's session is started only once the first claim's turn is spent. A claim that goes to a session of the owner (a record, a claim the owner asserted) is spent by that session, and `verify_one()`'s session spends its own (it names its claim: ending it leaves that claim's turn where it was, with no claim behind it).
  * *Freshness is judged at the moment of reading.* `_verdict()` compared `verified_at + max_age` and `expires_at` with `now()`, the start of the reader's transaction: in a READ COMMITTED transaction begun before the horizon, `brief()`, `truth_coverage()` and `_verdict()` served `verified` past it, after that transaction itself could see the claim was false. Now every read path compares with `clock_timestamp()`: `_verdict()`, the filter that hides an expired claim from `find()`, `find_hybrid()`, `find_npu()`, `find_ivf()`, the replacement chain and the recall measure. Not `statement_timestamp()`: one long statement (a `DO` block, a function that reads `brief()` in a loop) is a reader too.

* **Every wait a proof makes is seen, and a turn is spent only when its claim can be tried (thirteenth review).** The thirteenth review found two places where the twelfth review's rules held only in the common case:
  * *A proof runs in one process.* The lock rule above reads the proof's session: when its deadlock timer was last armed, and the lock it waits for when its clock ends. A proof's query could run in parallel workers, and a wait for a lock there was the worker's: the proof's session waited on the `Gather`'s queue, and a lock another session held past the clock got a true claim recorded `refuted` ("the proof took longer than 1000 ms"). The author needed only settings of its own role (`debug_parallel_query`, or a parallel plan with `parallel_leader_participation` off); a role that may `LOCK` a table the proof's functions read did the rest. Now the proof's session pins `max_parallel_workers_per_gather` and `max_parallel_workers` to 0 and `debug_parallel_query` off before it connects, over the database's and the role's settings, a `SET` in the proof and a function's `SET` clause (all of a lower source): no part of a proof runs in another process, and every wait it makes is its session's. The parallel workers' waits are not watched instead: a worker's deadlock timer and the lock it waits for are its own, and sampling `pg_locks` from the leader misses short waits. A proof's plan, and its estimated cost (`p_max_cost`), are those of a plan with no parallelism.
  * *A turn is spent only once a session can try its claim.* `verify()` needs two background workers at a time: the keeper, which spends the turns, and a session of the claims' author, which tries them. The keeper started first: when it took the last free slot, it spent the turns of the whole batch, no session of the author could start, and every claim of the batch was 'not judged' with its turn spent. Now the author's session starts first, then the keeper, and no turn is spent before both run; when either cannot start, the claim is not judged, nothing is recorded, it keeps its turn, and the call goes on without waiting for a slot. When the next author's claims come up, the session of the one before is waited for (up to 5 s) until it has left its slot: with no other slot free, the next one did not start, and its claims were 'not judged' with their turns spent, with no one holding anything. * **Cleanup that can run twice, a judgment that is one instant, and an update in its writers' order (fourteenth review).** The fourteenth review found:
  * *A cancelled verifier restarted the server.* When `verify()` goes from one author's claims to the next, it waits (up to 5 s) for the session of the one before to leave its slot. Shared memory was corrupted, the backend PANICked ("stuck spinlock detected at shm_mq_detach_internal") and the server ended every session and restarted: any role that may call `verify()` could do it by cancelling its own call. Now the cleanup of a proof's session can run again on whatever is left of it: each queue, the segment and the session are cleared before they are freed, and the session leaves the call before the wait, waiting where the call's cleanup ends and frees it if the wait is interrupted. The call's cleanup lets go of every session it has (its author's, its keeper, one still leaving), on an error and at its end alike. The other cleanup paths were checked for the same pattern: the keeper is stopped without a wait, a worker's own error ends its process, and a verifier that exits ends every session it has.
  * *A judgment's clock, snapshot and stamp are one instant.* `verify_one()` waits for its claim's row when another verifier is judging it. Its worker began the transaction that judges (whose start is the proof's `now()`) and then waited for the row in it: the proof read a clock from before the wait, a snapshot from after it, and its verdict was stamped after it. With two verifiers of one claim, an invoice that fell due during the wait was not past due by the proof's `now()`: `verified`, stamped after the due date, and served fresh for a whole `max_age`; and a heartbeat written during the wait was "in the future": a true claim stored `refuted`. Now the worker takes the claim without waiting (`SKIP LOCKED`), in the transaction that judges it; when another session holds it, it waits for it in a transaction of its own that judges nothing, and tries again in a new one. And `verified_at` is the proof's own `now()`, the start of the transaction that judged it, not a moment later: a verdict is never fresher than the clock it read. Each statement of a proof still reads a snapshot taken when it starts, after `now()`, as every statement under READ COMMITTED does; between the two there is no wait for the claim any more (since the fifteenth review not even a read of the claim's row: below).
  * *The update takes the extension's tables in its writers' order.* A writer takes the watched table, then `phasevec.watches` (the watch trigger reads its watch), then `phasevec.truth` (an `assert()` in the same transaction, from a trigger). The update script altered `phasevec.truth` and then `phasevec.watches`: a writer holding `watches` on its way to `truth` and the update holding `truth` on its way to `watches` deadlocked, and one was aborted. Now the script locks `watches`, `sources`, `lexstats`, `lexdocs` and `truth`, in that order, before anything else: the update waits for such a writer, and neither fails. DDL on a watched table in the same transaction as the update can still deadlock with that table's writers (it waits for them while the update holds what they wait for): run the update alone (*Upgrading from 0.19.0*, below).

In the second cut `brief()` ran the recipe as its caller with full rights: a table owner swapped a column's type for one whose cast was its own code, and a superuser reading the brief made it superuser. And a row's text depended on the session that read it: a writer in another `TimeZone` edited a row so that it printed as the text its author had vouched for, and `brief()` served it `verified`.
* **A proof means what it meant to its author.** `assert()` records, in `truth.proof_env`, what the author's session changed over the configuration a new session of the author starts from: every setting it set (`SET`, `set_config`, its startup options) of those that can change what a value reads, prints or computes -- every setting a user can set (and `RESET ALL` resets) of the groups statement behavior, locale and formatting, other client defaults and compatibility, and every custom setting (`app.tenant`, an extension's) --, its `application_name`, and every custom placeholder the session made, with a value or not (`app.tenant=`), since whether one exists is part of what `current_setting('app.tenant', true)` reads (NULL, or `''`). The proof runs in a new session of its author (above) with those on top, so the verifier's own settings decide nothing. What the configuration gives (`postgresql.conf`, `ALTER SYSTEM`, `ALTER DATABASE` and `ALTER ROLE ... SET`) is not recorded: it is the database's, as its rows are, and a proof reads it as it is when it runs; a change to it can change a verdict, as a change to a row can. In the eighth review a custom setting made at database or role level (`ALTER DATABASE ... SET app.x`) was in every new session, and the seventh cut judged no claim asserted before it again, in any session, and they filled the head of the queue (`p_n`): a new session of their author has it now, and judges them. A claim recorded before the eighth review recorded every setting off its built-in default, the configuration's too: those are set on top as recorded. Not recorded: resources, the planner, logging, statistics, replication and connections (they change how fast, not what), the session's timeouts, `client_encoding`, `client_min_messages`, `lc_messages`, `dynamic_library_path` and `extension_control_path`. In the second cut a verifier in another `DateStyle` read the author's `'01/11/2026'` as 11 January and recorded `verified` for a date the proof, as written, refutes; the third recorded twelve named settings, and a verifier's `default_text_search_config`, `timezone_abbreviations`, `transform_null_equals`, `row_security`, or the custom setting a row-level security policy read, decided the verdict (`test/sql/truth_sealed.sql`).
* **A placeholder made for one claim decides no other.** A custom setting no library defines (`app.tenant`) exists in a session once anything named it (`SET`, `set_config`, `RESET`, the configuration), and nothing removes it: a rollback takes back its value, not it, and `current_setting('app.tenant', true)` then reads `''` where it read NULL. In the seventh cut the guard set such a setting "to its default", which read `''` too, so it could not tell one that exists from one that does not: a proof that only called `set_config('app.tenant', 'acme', true)`, judged first in a `verify()`, changed what a later author's row-level security policy let its proof see, and a pooled verifier connection that once ran `SET LOCAL app.tenant` recorded, and `brief()` served, `verified` for a claim the persistent state refutes. The seventh cut judged a claim only in a session whose placeholders were its author's and left the others "to a new session"; in the eighth review a claim asserted again between runs, whose proof called `set_config` on a new name, came first in every run (it had no verdict yet) and kept every later claim of the run from being judged, in every new session, while their data changed. Now a worker notes the placeholders it started with (its configuration's) and judges a claim only while it has no other one than those and the ones the claim's author had; a worker that made one more (a proof's `set_config`, a recorded state that names one, a recipe that sets one) ends, and the claim goes to a new worker. A call sends each author's claims that name fewer placeholders first, so few workers end that way (`test/sql/truth_placeholder.sql`, `test/sql/truth_own_session.sql`).
* **A session that ends is the proof's failure only when the proof ended it.** A proof that ends the session it runs in (a `FATAL`, a C function's; since the tenth review no longer its author's `transaction_timeout`, which the worker does not take, below) ends its worker, not the verifier: the claim is recorded `refuted` and halted (`truth.halted`), is not run again until it is asserted again, and the rest of the call is judged in a new worker. Until the ninth review any end counted: a role with `pg_signal_backend` (or the author, or the verifier from another session of its own) terminated the worker, and a true claim was refuted and halted for good and left `brief()`. The worker notes who sent it `SIGTERM` (the sender's process id, which the kernel fills in and the sender cannot choose): ended by another process, the claim was interrupted. Nothing is judged, its verdict stays as it was (until its horizon), and it stays due, its turn spent (`truth.interrupted_at`, `interrupted_why`; `phasevec.attempts.why`). A signaller can keep a claim from being judged, never decide its verdict; halting a claim whose worker was ended some number of times would let a signaller that ends it that many times decide it. Until the eighth review that session was the verifier's own: nothing of the call was written, the claim was marked in shared memory, and the next `verify()` recorded it (in the second cut nothing marked it, and every later `verify()` died the same way; in the third the mark had no key, and one ended session halted every claim of the watch whose text, proof and author read alike, and of more than eight ended sessions the ninth mark was dropped; in the sixth a rolled-back `verify_one()` erased one). There are no marks now: a worker of the verifier that ran the proof records the halt (or the interruption) in a transaction of its own, for a verifier that may act as the claim's author; one that may not neither writes nor locks the claim, and the author's `assert()` of that key does not wait on it. A claim asserted again after its proof began is not the one that ran: it runs (`test/truth_race.sh`, `test/truth_worker.sh`).


* **A verdict is about a claim, and the claim is the text its author read.** `assert()` reads the row through the watch's recipe (rendered as above) and records the hash of that text (`truth.asserted_for`) with its author. A verdict judges that text, the proof, the author and its settings together, and records a binding of the four (`truth.verified_for`). A writer who edits the row afterwards changes the text, not the claim: the key reads `unproven`, `verify()` does not judge the new text whatever the proof reads, and it is a claim again when its author (or `adopt()`) asserts it again. Until 0.19.0 a row edited after it was verified kept `verified`, and `brief()` served its new text as verified; the first cut verified any new text again when the proof did not read the row (`test/sql/truth_binding.sql`, `test/sql/truth_claim.sql`). An author must be able to `SELECT` the table it asserts about (and, with row-level security, see the row), at `assert()` and at every `verify()`.
* **The row is read, not a cache.** `verify()` reads the live row before and after the proof, each time with a new snapshot. `brief()` hashes the line it serves and serves it as `verified` only if it is the text the verdict judged. `phasevec.sources.text_hash`, kept by the watch trigger, is not evidence: a change the trigger never saw (`ALTER TABLE ... DISABLE TRIGGER`, `session_replication_role = replica`, `TRUNCATE` and a new `INSERT`, `ALTER COLUMN ... TYPE ... USING`, a renamed column with a new one under its name, a hand-edited dump) reads `unproven` in `brief()` and is not verified by `verify()` (`test/sql/truth_claim.sql`, `test/dump_roundtrip.sh`).
* **A writer never waits on a verifier, and two verifiers do not wait on each other.** Whether a verdict still holds is read, not written: a `verified` or `refuted` whose row's text is not the one it judged reads `unproven` (`_verdict()`), and `verify()` takes such a claim first. `verify()` takes each claim's row before it judges it, and leaves one another transaction holds (another `verify()`, an uncommitted `assert()`): two `verify()` calls of one watch share it out. In the fifth cut a trigger on `phasevec.sources` wrote the verdict as the text changed, so a write waited on every open transaction that had judged that key, and two `verify()` calls of one watch locked its verdicts in different orders. Under writes (three clients editing texts, one editing them and back, two closing tasks) and two `verify()` loops over 1000 proofs, 20 s: a writer took 14.6-23.2 ms per edit (0.19.0: 0.17 ms; now 0.18-0.19 ms), 44-60% of the `verify()` calls died as deadlocks, each losing every verdict it had reached (0.19.0 and now: none; now 876-900 calls in 20 s, 0.19.0: 552) (`test/truth_locks.sh`). Measured again for the seventh review (PostgreSQL 19, 1000 claims each reading its row, three clients editing texts, one editing them and back, two closing tasks, two `verify()` loops over all of them, 15 s, three interleaved rounds on a loaded host): an edit took 0.18-0.19 ms (sixth cut 0.19-0.28 ms, 0.19.0 0.14-0.15 ms), with no deadlock and no failed call in any of the three; the two loops made 730-822 `verify()` calls (sixth cut 904-1150, 0.19.0 348-359). A claim whose row comes back to the text it judged is judged again now, where the sixth cut had written it off as `unproven`. Without writers a `verify()` of the 1000 claims took ~69 ms then (sixth cut ~65 ms, 0.19.0 ~30 ms; medians of four); for what it takes since the eighth review, see the cost below.
* **A verdict stays bound to the text it judged.** A claim whose row says something else (or is gone) reads `unproven` while it does (`_verdict()`); `verify()` looks at it once for each text it reads, records that it looked (`truth.looked_at`, `looked_for`) and leaves the verdict, which reads `verified` or `refuted` again if the text comes back. In the sixth cut `verify()` wrote `unproven` over it: a writer that edited a row for a moment, while a routine `verify()` ran, erased a refutation until the claim was due again (`p_every`), while `_verdict()` read `refuted` as soon as the text was back (`test/sql/truth_stale.sql`).
* **The watch trigger's plan follows its table.** The trigger prepares its reading of a row once per session and watch, and keeps it with the table's row type (the columns' names, types, typmods, collations, and the dropped ones): when those change, it prepares it again. In the fifth cut it kept it until the session reconnected, and the plan reads the row by column number: a session that had written before a `RENAME`, a `DROP` and `ADD COLUMN` or an `ALTER COLUMN TYPE` hashed the old column (an edited row stayed fresh, `next()` handed out nothing and `find()` served the old reading), or failed every later write with "attribute N has wrong type" -- every connection of a pool, after a migration (`test/sql/truth_plans.sql`). A partition's row is read as a row of the watch's table, in its columns and their order: in the sixth cut the trigger read it in the partition's own row type, and `_render()` and `verify()` in the table's, so on a partition whose columns stood in another order (attached, or after a `DROP` and `ADD`) a recipe that uses the whole row (`r::text`, `row_to_json(r)`) noted another text: its claims never read as asserted, asserted again or not, and its rows were indexed with that text (`test/sql/truth_partition.sql`).
* **One state.** Under READ COMMITTED each statement of a proof can see another snapshot. The row's version (`xmin`, `ctid`) is read before and after the proof; if it moved, nothing is recorded and the key stays due. A text that changed and changed back while its proof ran was recorded `verified` for a text the proof never saw (`test/truth_race.sh`). A proof is judged at READ COMMITTED, in its own session, each statement in a new snapshot of what is committed; the verifier chooses, takes and records its claims at READ COMMITTED too (it refuses REPEATABLE READ and SERIALIZABLE); `verified_at` is when the row was read for the verdict: in the third cut a verifier in a REPEATABLE READ transaction judged every proof against its first snapshot and recorded the verdicts as reached then (`test/sql/truth_sealed.sql`).
* **A proof runs as its author, by OID.** `assert()` records its caller's current user (`truth.asserted_by_oid`, and in `truth.asserted_by` the name it had); a `SECURITY DEFINER` wrapper vouches with its owner's rights. `verify()` runs each proof with that role's rights, in the guard, only when the caller already holds them; `verify()` skips the others, `verify_one()` refuses them. A dropped author, or one whose name now belongs to another role, runs nothing: the claim reads `unproven` until it is asserted again. A verdict is recorded only for the author it ran as: an `assert()` of the same proof by another role while it runs leaves nothing recorded. Until 0.19.0 a proof ran with the rights of whoever called `verify()` (`test/sql/truth_author.sql`, `test/sql/truth_door.sql`, `test/truth_race.sh`).
* **One door.** `verify()` and `verify_one()` are C: they know who calls them and pass that to the internals, which carry no rights of their own (only the owner can read and write `phasevec.truth`). A verifier other than the owner is granted `verify()` or `verify_one()` and nothing else. The first cut had verifiers granted `SECURITY DEFINER` internals, and with them a verifier forged `verified` and read every proof (`test/sql/truth_door.sql`).
* **The clock bounds the verdict.** Every proof has a clock: `p_timeout_ms` must be above 0, because the cost cap is a planner estimate and not a bound. A verdict counts only if the proof ended inside its clock, so a proof that catches `query_canceled` runs on but is refuted for its time. A proof cannot run another proof. A `query_canceled` that a proof raises itself is that proof's error (it aborted every `verify()` of the watch); the caller's `statement_timeout` and a user's cancel still cancel the statement. A session-level advisory lock a proof takes is released when it ends (`test/sql/truth_deadline.sql`). The worker runs each proof under its clock; the verifier waits for its answer that long and 5 s more, then ends the worker, and a new one records the claim refuted for its time.
* **A proof is one expression, under the cost cap and the clock.** A proof that closed its own parenthesis made two statements: the cost step ran the second one with no clock and no cap. The wrapped proof is now parsed and must be one `SELECT`; a cost that cannot be read is refused; and the proof's clock runs from before the estimate, which can run immutable functions while planning (`test/sql/truth_cost.sql`).
* **Closed to `PUBLIC`, and to the wrong writer.** `_forget()` (callable from any user's own trigger) is the owner's only. The watch trigger (`phasevec._observe()`) is C: it renders the row it fires for, and refuses to run on any table but its watch's. `_note()`, which took a key and a hash from whoever called it, is gone: in the first cut whoever was granted it for one table forgot, rewrote and invented the keys of every other watch, and in the second a writer limited by row-level security, or holding `UPDATE` on one unrelated column, did it to every key of its own watch. `recall()`, `disputes()`, `replacement()` and `truth_coverage()` are one C door that shows a watch only to a role that may `SELECT` its table, and with row-level security it computes over the rows that role sees, so no field carries another (in the third cut `recall()`'s `disputed_by` named keys of hidden rows, and `replacement()` followed a chain through a hidden row and showed its reason; `truth_coverage()` now counts that role's rows); until 0.20.0 any role with `USAGE` on the schema read every watch's keys, verdicts, topics, reasons and support through them. `brief()` is the same kind of door; it is revoked from `PUBLIC` and granted alone (`_brief_keys()` is its internal, the owner's) (`test/sql/privileges.sql`, `test/sql/truth_guard.sql`, `test/sql/truth_sealed.sql`). A watch's key is a column with a unique index of its own: in the third cut two rows could share a key, and a writer limited by row-level security, deleting its own row, forgot the other's key and its verdict.
* **The coarse index is checked as it loads, and every time it is used.** Every blob of `phasevec.ivf_lists` and `phasevec.ivf_added` is checked for `NULL` and for its exact length, every count for its sign, and every key offset for its place inside the keys, before anything is copied: those rows travel in `pg_dump` since 0.19.0, and a truncated or edited one made the loader read out of bounds. A copy kept in memory (by the connection or shared by the cluster) is checked against its row of `phasevec.ivf_cents` every time it is used, and `ivf_absorb` grows it only if it is the index it read: a row edited under the same version made `ivf_absorb` size its lists from the row and grow the copy with them, a write past the end of a buffer (`test/sql/ivf_blobs.sql`). `ivf_absorb` checks it with the shared copy or without one: until the sixth cut only with it, so on PostgreSQL 18, where there is none, an edited row was absorbed in its own shape.

**Upgrading from 0.19.0** (`test/sql/upgrade_020.sql`). Every `verified` goes back to `unproven`, with the reason in `last_error`: it was reached with the verifier's rights, about no claim. `refuted` stays refuted, about the text the row has now. Every row of every watch is rendered again in the pinned settings; a text that reads otherwise now (a recipe that prints a date, a time, a float or a money value, or calls a function the table's owner may not run) is noted again: its reading turns stale and its verdict `unproven`. The upgrade fails if a recipe cannot run as its table's owner, read-only. Proofs asserted before 0.20.0 have no author and do not run until they are asserted again. `phasevec.adopt(watch, author)` asserts them again in the name of the role it is given: the caller must hold that role's privileges (be it, `SET ROLE` to it, or be granted it); it is the owner's to run or to grant; it returns every proof with its former author; and a superuser becomes the author only of the keys named in `p_superuser_keys` (an orphaned proof may be anyone's SQL, and a role can orphan its own on purpose). Adopt as the least-privileged role that can read what the proofs read. Naming an author in `phasevec.truth` by hand is not enough, a claim is also the text its author read. Calls of `verify()` and `verify_one()` keep working, except with `p_timeout_ms => 0`. `brief()` is granted alone; grants on `_brief_keys` are gone. A trigger of your own that asserts claims must fire on every column the recipe reads: an edit of a column it does not watch leaves the claim `unproven` until it is asserted again. A recipe that writes, or that the table's owner cannot run, now fails wherever it runs, including in the watch trigger on every write to the table. A database that ran an unpublished cut of 0.20.0 cannot be updated in place to this one (same version): drop and create the extension, or dump and restore the database (its proofs then wait for `adopt()`). **Reconnect after the update** (or restart the server): a session that loaded the library of 0.19.0 keeps it, and the new watch trigger is not in it. Its writes to a watched table are refused with a message that says so (the trigger is in a library of its own, `pg_phasevec_observe`, installed with the extension, which no older session has loaded); its calls of the new C functions (`verify()`, `brief()`, `recall()`, ...) fail with "could not find function" (`test/upgrade_reconnect.sh`). **Run the update alone**: `ALTER EXTENSION pg_phasevec UPDATE` in a transaction of its own, with a short `lock_timeout` (it waits for the writers of watched tables, and they queue behind it), retried if it times out; not in one transaction with DDL on a watched table (`CREATE TRIGGER`, `DROP TRIGGER`, `ALTER TABLE`): that DDL waits for the table's writers while the update holds the extension's tables they are waiting for, a deadlock that aborts one side. The update itself takes the extension's tables in the order its writers do (`test/upgrade_locks.sh`). A trigger or function of yours that asserts claims as `SECURITY DEFINER` makes its owner the author of every claim it asserts from the update on (a superuser owner: proofs that run as superuser, and a verifier that may not act as it never judges them); `adopt()` does not take those back, its author is known. Make it assert through a function owned by the role that should author the proofs before the update (on 0.19.0 `assert()` has the same signature), then `adopt()` what was asserted before, and check that every claim with a proof, not replaced, has that author. The update warns about every watch whose key column has no unique index of its own: it keeps working, but add one. A proof or a recipe that called a volatile system function outside the reviewed list (`nextval`, `currval`, `pg_read_file`, ...) or `txid_current()`, ran a command other than those above, read a cursor its caller had open, or read a temporary table or called a temporary function, now fails (a proof is refuted with the reason). A temporary table cannot be watched. A watch over a table with `FORCE ROW LEVEL SECURITY` now renders every row (as the owner, without the policies).

**Limits.**

* A proof that catches `query_canceled` keeps its worker until it returns: the clock decides the verdict and cannot stop such a proof. The verifier waits for it its clock and 5 s more, records it refuted, and ends the worker (`TerminateBackgroundWorker`), which code that ignores interrupts (an extension's C function) can outlast, holding its slot of `max_worker_processes` until it returns. Grant `assert()` only to roles whose code you would run as them.
* `assert()` takes its author from whoever calls it. A trigger function that is not `SECURITY DEFINER` runs with the rights of whoever fires it, so its owner can assert in the name of anyone who writes that table, as it can do anything else with those rights: PostgreSQL's own trigger trap. phasevec cannot see who wrote the calling code.
* `_verdict(t)`, for SQL that reads `phasevec.truth` directly, compares the claim with the trigger's cache, not with the row: after a change the trigger never saw it says `verified` until the next `verify()` of the key, or its horizon. `brief()` and `verify()` read the row. It answers `NULL` for a claim whose watched table the caller may not `SELECT` (or whose row a policy hides from it): SQL that reads `phasevec.truth` as such a role reads `NULL` where it read a verdict before 0.20.0 (`coalesce(phasevec._verdict(t), 'unproven')` reads it as unproven). It decides who may see on every call, from the catalogs as they are (sixteenth review): under row-level security it reads the watch and looks the row up as the caller, two queries a row.
* `next()` and `audit_sample()` (fill and audit, not reading) run as their caller and use the extension's own internals and tables (`_todo`, `_watch`, `readings`, `kstate`): they are the owner's, or a role's that is granted those too. Granted alone, they are refused.
* A restore trusts its dump: a dump edited by hand can also rewrite `phasevec.truth`. After a restore into another cluster the roles have other OIDs, so every proof reads its author as gone until `adopt()`.
* The guard refuses functions when an expression is set up (PostgreSQL's function-execute hook). A PL/pgSQL expression a session's transaction already ran before a guard is cached without that check: a recipe that reaches that same cached expression in the writer's or reader's session is not refused (a proof's session runs nothing outside a guard). Functions that are not the system's (an extension's C function such as `dblink`) are not classified: they run with the role's rights. `random()` draws from the generator of the session the code runs in (a proof's worker's; a recipe moves its writer's sequence), which it cannot seed.
* A cursor a client opened through the extended protocol (a named portal, as JDBC uses with a fetch size) is not listed by `pg_cursors`: the guard refuses to run its query, but rows it already holds in memory (a portal over `INSERT ... RETURNING` read in part) can be read by a recipe that renders in that session, and it can close it; a proof's session has no such cursor.
* The settings a proof does not take from its author (resources, the planner, `max_stack_depth`, `work_mem`, the session's timeouts) are its worker's -- but for parallelism, which the worker pins off (thirteenth review) --, a new session's of its author: they can decide whether a proof runs out of memory, stack or time (refuted), not what it computes.
* Cost: every recipe or proof runs in a subtransaction of its own with its settings set, and every proof in a background worker. On a watch of 1000 proofs, each reading a row of another table, `verify()` from a new session takes ~105 ms on PostgreSQL 19 (0.19.0: ~30 ms; the eighth cut, 2f42e62: ~54 ms; medians of six, the three measured together) and ~450 ms on an assertion-enabled 18 (0.19.0: ~150 ms; 2f42e62: ~250 ms). Since the ninth review the worker takes, judges and records each claim and commits its verdict, where the eighth cut's worker judged a claim while the verifier took and recorded the one before, in its own transaction: what the verifier did alongside is the worker's now, about 50 us a claim. Starting a worker costs ~3 ms: `verify_one()` takes ~7 ms (2f42e62: ~6 ms; 0.19.0: ~1 ms), `verify(p_n => 100)` ~23 ms (2f42e62: ~15 ms; 0.19.0: ~5 ms). The tenth review's changes cost nothing measurable: `verify()` of those 1000 claims takes ~117 ms on 19 against ~117 ms at c1461cf (the same cluster, the library swapped between runs, medians of twelve; 0.19.0: ~40 ms), `verify_one()` ~6 ms; on the yggdrasil mirror ~115 ms (0.19.0: ~39 ms), and ~470 ms on an assertion-enabled 18 (0.19.0: ~175 ms). Of a claim's ~117 us in the worker, taking its row is ~9 us, judging it ~42, recording it ~42 (an `UPDATE` of the claim through `_truth_set`) and committing ~2: committing several claims in one transaction saved about 6% when measured, and is not done -- a verdict is committed before its answer goes back, and a session that ended in the middle of a batch would take the verdicts judged before it. On a mirror of yggdrasil's layout (claims asserted by `SECURITY DEFINER` triggers, verified by `pg_cron` as `ygg_lector`), `verify('estado')` of 1000 claims takes ~120 ms (0.19.0: ~55 ms; 2f42e62: ~61 ms). Before each claim the worker reads which custom placeholders it has (walking every setting: PostgreSQL offers no cheaper way); `brief()` ~18 ms (0.19.0: ~42 ms). Choosing the due claims reads every claim of the watch: `verify(p_n => 100)` costs more as the watch grows (the seventh review measured ~18 ms at 1000 claims and ~77 ms at 20000; 0.19.0 stayed at ~12 ms). The watch trigger renders each written row in its own guard: an `UPDATE` of 1000 watched rows, whose recipe joins another table, takes ~57 ms (0.19.0, which noted the row in PL/pgSQL without a guard: ~46 ms; the fourth cut of 0.20.0, which parsed and planned three statements for every row: ~210 ms), as much from a session that has a temporary table, and since the sixth cut from one that writes to it in the same transaction (a single-row write with `pgbench -M prepared`: 0.09-0.11 ms, the sixth cut 0.55-0.56 ms, PostgreSQL 19; on an assertion-enabled 18: 0.58 ms, the sixth cut 1.58 ms). Inside the guard no SQL function but the system's is inlined: a recipe or a proof that calls one runs it as a call. The statements it runs for a row are prepared once per session and watch; what a row still costs is its guard (a subtransaction, the settings set and rolled back) and reading the session's settings, which it does for every row (~17 us of the ~60): PostgreSQL offers no cheap way to know exactly that none changed since the last row, and a cache could miss one a writer set between two statements. The eleventh review's rules cost one more transaction per claim (the worker spends the claim's turn, ~20 us) and a lookup of the watch's `max_age` per verdict read: `verify()` of those 1000 claims takes ~148 ms on 19 against ~128 ms at 07b019f and ~42 ms for 0.19.0, `verify(p_n => 100)` ~31 ms (07b019f: ~28; 0.19.0: ~9), `verify_one()` ~9 ms (07b019f: ~9; 0.19.0: ~1.4), and on an assertion-enabled 18 ~594 ms (07b019f: ~554; 0.19.0: ~245), the three interleaved on one machine, medians of 21 (14 on 18); `_verdict()` over 2000 claims ~13 ms against ~11, `brief()` of 1000 lines ~45 ms against ~40. Measured at 60x speed (a call every 10 s for every 10 minutes, `p_every` and `max_age` scaled alike), 1000 claims with `p_n` 100 settle at 600 fresh and 400 `unproven` (each claim comes round every 100 minutes, past the default hour); with `p_n` 2000 all 1000 stay fresh, each judged every 10 minutes. The twelfth review's keeper costs nothing measurable: it spends turns in batches (when the worker is about to run out of spent claims, or half a queue waits), while the worker, which no longer spends them, judges the claims ahead. `verify()` of those 1000 claims takes ~117 ms on 19 against ~115 ms at 4f966eb and ~29 ms for 0.19.0, `verify(p_n => 100)` ~21 ms (4f966eb ~21; 0.19.0 ~5), `verify_one()` ~6 ms (4f966eb ~6; 0.19.0 ~1.2); on an assertion-enabled 18 ~480 ms (4f966eb ~483; 0.19.0 ~138), `verify(p_n => 100)` ~75 ms (~77; ~21) (the three interleaved, medians of twelve). On the yggdrasil mirror under load (writers, cancelled and terminated verifiers, DDL, `pg_cron` running `verify('estado', 5000)`), `verify('estado')` of 1000 claims takes ~140 ms (0.19.0 in the same run ~50 ms), with no verdict wrong against the committed state as of when it was judged. * `assert()`, `verify()`, `brief()` and the rest find a row by `key_col::text = key`, through the key column's index when its type is an integer, `oid`, `numeric` or `uuid`, by a scan otherwise.
* A recipe sees, beyond its row, what the table's owner may see (a subquery in it runs with the owner's rights), and its text goes to any role that may `SELECT` the table.
* `verify()` leaves a claim whose row another transaction holds (an `assert()` not committed, by any role that may assert, or another `verify()`), its turn spent: a later call judges it, and until then its verdict serves until its horizon. `verify_one()` waits for it instead (since the tenth review before it judges: below). An `assert()` of a claim waits for the worker judging it, up to the proof's clock and the record. Each verdict is committed by its proof's session as it is reached: a `verify()` that is cancelled, or whose transaction aborts, keeps the verdicts it reached (`p_budget` ends a call cleanly). A transaction that has written may not verify: an `assert()` and a `verify()` of its claim go in two transactions.
* A worker that made a placeholder the next claim's author did not have ends, and a new one starts (~3 ms): a watch whose proofs each make a new one (`set_config` of a name per key) pays a worker's start per claim. A claim recorded before the seventh cut of 0.20.0 names only the placeholders that had a value: it reads as if its author's session had no other. A setting a library defines (`plpgsql.*`, an extension's) exists once the library is loaded in the session; whether it is loaded is not compared.
* A recipe reads custom placeholders as the session that renders it has them (the writer's, for the watch trigger), each set to `''`: a recipe that reads `current_setting('app.x', true)` renders a text that depends on whether that session ever named `app.x`. Where that text is not the one its author vouched for, the claim reads `unproven`; it is never verified, nor served, for it.
* A recipe runs in the writer's session (the watch trigger) and a row-level security policy in the reader's, as PostgreSQL runs an index expression or a policy: the walk refuses what they name of that session's temporary objects, but a name they look up while they run (`to_regclass(text)`, a cast of text to `regclass`) can find one. The text noted then is not the one `_render()` reads, and the claim reads `unproven`; it is never verified that way, because `verify()` judges only in a session without them. A proof or a recipe that reads the catalogs as data (`pg_class`, `pg_type`) sees every session's temporary objects there, as any query does.
* The walk for temporary objects covers relations, types (a domain's base, an array's element), functions, operators and collations named in expressions, range tables and sort clauses, the `RETURNING` type of the SQL/JSON functions and the type of `XMLSERIALIZE`, and `regclass`-like constants (text search configurations and dictionaries, schemas); on PostgreSQL 19 PostgreSQL's own walk (`collectDependenciesOfExpr`) runs too. A node kind neither knows is not refused by it: in a proof that is moot (no temporary object exists where one is judged), in a recipe it is the limit above.
* A halt, an interruption, a claim refuted for its time, the `unproven` of a gone author and a claim its author's sessions could not judge are recorded by a worker too (a new one after one ended; one connected as the extension's owner when no author's is at hand): with no slot of `max_worker_processes` free for 5 s it is not recorded, and the claim stays due (a halted one runs again, and ends another worker). A proof that crashes the server (C code that dies with a signal) restarts it, verifier and all.
* A session another process ends while its proof runs is interrupted, not halted, whoever ended it: a proof that has another session end its own (through an extension such as `dblink`) is interrupted at every run, its turn spent each time, and reads `unproven` past its horizon. A shutdown interrupts the claims being judged.
* A proof waits for a lock up to its clock; then it is not judged, and since the twelfth review neither is one that waited for a lock and then ended after its clock. An author can therefore keep its own slow proof from being refuted for its time by making it wait for a lock it holds: it is not judged, and reads `unproven` past its horizon, never `verified`. Only waits for heavyweight locks are told apart: a wait for a lightweight lock or a buffer another session holds (short, and not held across statements) counts as the proof's time. They are the waits of the proof's session: since the thirteenth review a proof runs in one process (no parallel worker), so every one it makes is seen; a proof that reaches another session (an extension's code: `dblink`, `postgres_fdw`) waits there unseen, and that time counts as the proof's. A writer that holds a table a proof reads for longer than the proof's clock keeps its claim from being judged, and its verdict serves until its horizon; until the eleventh review it made the claim `unproven` at once, which let any session that can take a lock a proof waits for (an advisory lock needs no grant) erase a true claim's `verified`. A verifier whose transaction holds what a proof waits for gets an error (its transaction aborts; the verdicts reached before it stay, committed).
* A proof whose author is a superuser runs as a superuser: read-only and security-restricted, but with every right to read. Adopt orphaned proofs with a role of your choosing, not as the owner by default.
* A verifier that may act as an author runs that author's code, in a session of that author: grant `assert()` only to roles whose code you would run as them.
* A proof's session is a background worker: a call uses one at a time, and `verify()` one more, its keeper (twelfth review), while it has claims for an author's session: two slots of `max_worker_processes`, which parallel query, logical replication and other extensions share (a proof itself starts no parallel worker: thirteenth review). Leave two free for every `verify()` that may run at once, one for every `verify_one()`. Both of `verify()`'s are started before a claim's turn is spent: a claim found with no slot free for either is not judged, nothing is recorded, and it keeps its turn -- nothing about the claim or its author kept it from being judged -- and the call goes on without waiting for one (until the thirteenth review the keeper could take the last slot and spend the turns of a batch no session could try). Once a claim's turn is spent, a new session of its author is needed only after the one started for it ended (its proof ended or overran it, a placeholder, its author ended it): if no slot is free then, the claim is not tried, its turn stays spent, and its verdict serves until its horizon, as when its author ends its sessions. While no worker is free nothing is judged, and every verdict serves until its horizon and then reads `unproven`. The keeper is a session of the extension's owner: a role that may end the owner's sessions (a superuser; with `pg_signal_backend` when the owner is not a superuser) can stop a `verify()` call, and nothing more -- nothing is judged or recorded, the claims keep their turns, and the verdicts serve until their horizon.
* `verify()` and `verify_one()` refuse a read-only transaction, session or standby (sixteenth review): a job that verifies runs in a session that may write (yggdrasil's `pg_cron` job does: `SET ROLE` does not make it read-only).
* Whether an author may still read the watched table is read once per `verify()` call: a `REVOKE` during a long call does not stop its proofs from running, and a proof that then reads the table fails with its own permission error, which is its answer (refuted). The next call records it `unproven`.
* A `DROP ROLE` of an author waits for the verdict its worker is judging (up to the proof's clock and 5 s): the worker holds the role until the verdict commits.
* `become()` pins the settings that decide what phasevec's own statements read and compute, not `session_replication_role` (a superuser's): a superuser session set to `replica` keeps the extension's internal triggers (its counts) from firing, as for any table.
* A proof reads what any session of its author reads, the others included (`pg_stat_activity`, `pg_locks`), and its verifier's session is one of them.
* The configuration is the database's: a role that may change it (`ALTER DATABASE ... SET` is the database owner's; `ALTER ROLE ... SET` a role admin's, and any role's for itself for a setting a user may set) changes what proofs read, as a role that may write a table changes what they read of it. The session timeouts and `exit_on_error` are not part of it: a worker pins them before it connects (tenth review; until then this line said a `transaction_timeout` set there was a role admin's and halted the claim, and an ordinary author that set its own to 1 ms had every worker of its claims end before it judged, its claims never judged again and still `verified`). What else it sets can keep a new session of the author from starting at all (a `local_preload_libraries` that fails to load): its claims are then tried and not judged, and read `unproven` past their horizon. An author, or anyone who can hold a claim's row or a lock its proof needs, can keep a claim from being judged, not keep its verdict past the horizon; until then a verdict about the state before can still be served. The horizon is the bound: choose `max_age` for what a stale verdict costs you, and make the rotation fit inside it.
